## 섹션 1: 도메인 모델 — Bookmark

**Q1. 북마크 읽음(read) 상태 관리**  
인박스에서 "읽음 처리"가 있는데, 읽음 상태를 어떻게 정의하시나요?

A) 사용자가 명시적으로 "읽음" 버튼을 클릭해야만 읽음 처리  
B) 북마크 상세 보기(URL 클릭 또는 모달 열기) 시 자동으로 읽음 처리  
C) A + B 모두 (명시적 버튼 + 자동 처리)

> **추천: A**  
> 인박스는 "처리해야 할 항목 목록"의 성격이 강합니다. 이메일 클라이언트처럼 열람만 해도 읽음 처리되면 사용자가 의도치 않게 상태가 바뀌어 혼란스럽습니다. 명시적 액션(버튼 클릭 또는 체크박스)으로만 읽음 처리하면 사용자가 인박스를 "할 일 목록"처럼 관리할 수 있고, 구현도 단순합니다. B나 C는 자동 처리 로직이 추가되어 복잡도가 올라가고 MVP에서 불필요한 오버엔지니어링입니다.

[Answer]: C

**Q2. 북마크 삭제 시 컬렉션 블록 처리**  
북마크를 삭제할 때, 해당 북마크를 참조하는 컬렉션 링크 블록은 어떻게 처리하나요?

A) 링크 블록도 함께 삭제 (cascade)  
B) 링크 블록은 유지하되 북마크 참조(bookmark_id)만 null로 변경, URL/제목은 블록에 복사본으로 보존  
C) 삭제 전 경고 팝업 표시 ("이 북마크는 N개 컬렉션에서 사용 중입니다")

> **추천: B**  
> 요구사항(FR-05-2)에 "삭제 시 링크 블록이 참조하는 북마크 원본은 유지"라고 명시되어 있고, 반대로 북마크 삭제 시에도 컬렉션 블록은 유지하는 것이 자연스러운 대칭 설계입니다. 컬렉션은 공개 공유 목적이므로, 내부 북마크를 삭제했다고 공개된 컬렉션 링크가 사라지면 공유받은 사람 입장에서 콘텐츠가 깨집니다. B는 블록에 URL/제목 스냅샷을 보존하므로 공개 페이지 무결성을 지킬 수 있습니다. C는 UX 마찰이 크고 MVP에서 과도합니다.

[Answer]: B

B) 별도 Block 테이블로 변경 (FK 관계, 정규화)

**Q5. 컬렉션 슬러그 자동 생성 규칙**  
컬렉션 생성 시 슬러그를 어떻게 자동 생성하나요?

A) UUID 기반 short ID (예: `abc12345`) — 완전 랜덤, 충돌 없음  
B) 컬렉션 이름 기반 slug (예: `my-collection`) + 중복 시 숫자 suffix (예: `my-collection-2`)  
C) nanoid 등 URL-safe 랜덤 문자열 (예: `V1StGXR8`)

> **추천: C**  
> nanoid(길이 8~10)는 URL-safe 문자만 사용하고, 충돌 확률이 UUID 수준으로 낮으며, 사람이 읽기에도 UUID보다 짧고 깔끔합니다. A(UUID short ID)는 충돌 방지는 되지만 hex 문자만 써서 미관상 덜 세련됩니다. B(이름 기반)는 한국어 컬렉션 이름을 slug로 변환할 때 인코딩 문제가 생기고, 중복 suffix 로직이 추가로 필요합니다. 사용자가 나중에 커스텀 슬러그로 변경할 수 있으므로 초기 자동 생성은 C가 가장 실용적입니다.

[Answer]: C

**Q6. 컬렉션 블록 — 링크 블록의 북마크 연결 방식**  
링크 블록을 추가할 때 항상 기존 북마크와 연결해야 하나요, 아니면 북마크 없이 URL만으로도 추가 가능한가요?

A) 항상 북마크와 연결 (북마크 먼저 저장 → 링크 블록 추가)  
B) URL만으로도 링크 블록 추가 가능 (북마크 연결은 선택사항)  
C) 두 경우 모두 지원 (북마크 연결 또는 URL 직접 입력)

> **추천: C**  
> 사용 시나리오가 두 가지입니다. ① 인박스/그룹에서 이미 저장한 북마크를 컬렉션에 끌어다 넣는 경우(북마크 연결), ② 컬렉션 편집 중 새 URL을 바로 추가하고 싶은 경우(URL 직접 입력). 두 경우를 모두 지원해야 편집 흐름이 자연스럽습니다. A만 허용하면 컬렉션 편집 중 매번 인박스로 이동해 북마크를 먼저 저장해야 하는 불편함이 생깁니다. C를 선택하면 URL 직접 입력 시 내부적으로 북마크를 자동 생성하거나, 블록에 URL 스냅샷만 저장하는 방식으로 구현할 수 있습니다.

[Answer]: C

## 섹션 3: 비즈니스 로직 — 인증 흐름

**Q7. Cognito 토큰 저장 위치 (웹앱)**  
웹앱에서 Cognito JWT 토큰을 어디에 저장하나요?

A) HttpOnly Cookie (XSS 방어, CSRF 고려 필요)  
B) localStorage (간단하지만 XSS 취약)  
C) 메모리(React state) + Refresh Token은 HttpOnly Cookie

> **추천: A**  
> Next.js App Router 환경에서 HttpOnly Cookie는 Server Component와 Middleware에서 자연스럽게 토큰을 읽을 수 있어 아키텍처와 잘 맞습니다. XSS 공격으로 토큰을 탈취할 수 없고, CSRF는 SameSite=Lax 설정으로 대부분 방어됩니다. B(localStorage)는 XSS에 취약해 보안 요구사항(NFR-02-3)에 위배됩니다. C는 페이지 새로고침 시 Access Token이 사라져 매번 Refresh Token으로 재발급해야 하는 복잡도가 생깁니다. Cognito의 Access Token + Refresh Token 모두 HttpOnly Cookie에 저장하는 것이 가장 단순하고 안전합니다.

[Answer]: A

---

**Q8. 최초 로그인 시 사용자 DB 레코드 생성 시점**  
Cognito 로그인 후 DB에 User 레코드를 언제 생성하나요?

A) 최초 API 요청 시 `getUserFromToken()`에서 없으면 자동 생성 (lazy creation)  
B) 회원가입 완료 시 Server Action으로 즉시 생성  
C) Cognito Post-Confirmation Lambda Trigger로 생성 (Unit 1 인프라 필요)

> **추천: B**  
> 회원가입 완료(이메일 인증 후) 시점에 Server Action으로 즉시 DB User 레코드를 생성하는 것이 가장 명확합니다. A(lazy creation)는 구현이 단순하지만, 최초 API 요청마다 "DB에 없으면 생성" 분기가 들어가 모든 Service 메서드에 부수 효과가 생깁니다. C는 Lambda Trigger가 필요해 Unit 1 인프라 의존성이 생기고 Unit 2 단독 개발이 어려워집니다. B는 회원가입 플로우가 명확하고, 이후 모든 API는 User가 반드시 존재한다고 가정할 수 있어 코드가 단순해집니다.

[Answer]: B

## 섹션 4: 비즈니스 로직 — 검색

**Q9. 검색 대상 범위**  
검색 시 어떤 데이터를 검색 대상으로 포함하나요? (복수 선택 가능)

A) 북마크 제목 + URL  
B) 북마크 메모  
C) 북마크 태그  
D) 컬렉션 이름 + 설명  
E) 컬렉션 블록 텍스트 (텍스트 블록 내용)

> **추천: A + B + C + D (E는 선택적)**  
> A~D는 핵심 검색 대상입니다. 사용자가 저장한 북마크를 찾을 때 제목/URL/메모/태그는 당연히 검색되어야 하고, 컬렉션도 검색 결과에 나와야 유용합니다. E(컬렉션 블록 텍스트)는 요구사항(FR-06-2)에 명시되어 있으므로 포함하는 것이 맞습니다. 단, 블록이 JSONB로 저장되므로 tsvector 인덱스 생성 시 JSONB에서 텍스트를 추출하는 generated column이 필요합니다. 구현 복잡도가 있지만 요구사항이므로 포함합니다. **결론: A + B + C + D + E 전체 포함.**

[Answer]: A + B + C + D + E 전체 포함.

**Q10. 검색 결과 정렬 기준**  
검색 결과를 어떻게 정렬하나요?

A) 관련도(relevance) 순 — PostgreSQL tsvector rank 기준  
B) 최신순 (created_at DESC)  
C) 관련도 우선, 동점 시 최신순

> **추천: C**  
> 검색의 본질은 "가장 관련 있는 것을 먼저 보여주는 것"이므로 관련도가 1순위여야 합니다. 그러나 tsvector rank는 동점이 자주 발생하는데, 이때 최신 항목을 먼저 보여주는 것이 사용자 기대에 부합합니다. A만 사용하면 동점 시 순서가 불확정적이고, B만 사용하면 검색의 의미가 퇴색됩니다. C는 두 기준을 합리적으로 결합한 표준적인 접근법이며, PostgreSQL에서 `ORDER BY rank DESC, created_at DESC`로 간단히 구현됩니다.

[Answer]: C

**Q11. 그룹 → 컬렉션 변환 시 원본 그룹 처리**  
`GroupService.convertToCollection()` 실행 후 원본 그룹은 어떻게 되나요?

A) 원본 그룹 유지 (북마크도 그룹에 그대로 남음)

**Q14. 컬렉션 편집 페이지 — 블록 추가 UX**  
컬렉션 편집 페이지에서 블록을 어떻게 추가하나요?

**Q15. 공개 컬렉션 페이지 (`/c/{slug}`) — 좋아요 UX**  
비로그인 사용자의 좋아요 버튼 동작은?

A) 바로 좋아요 가능 (익명, fingerprint 기반 중복 방지)  
B) 로그인 유도 팝업 표시 후 좋아요  
C) 좋아요는 로그인 사용자만 가능

> **추천: A**  
> 요구사항(FR-05-14)에 "좋아요 — 익명 가능, IP+User-Agent 기반 중복 방지"라고 명시되어 있습니다. 공개 컬렉션의 핵심 가치는 "누구나 접근 가능한 공유 페이지"이므로, 좋아요에 로그인 장벽을 두면 반응률이 크게 떨어집니다. fingerprint 기반 중복 방지로 어뷰징을 충분히 막을 수 있습니다. B나 C는 요구사항에 위배되고, 공유 페이지의 바이럴 효과를 저해합니다.

[Answer]: C

**Q16. 모바일 반응형 — 그룹 대시보드**  
모바일에서 Toby 스타일 컬럼 레이아웃을 어떻게 표시하나요?

A) 가로 스크롤 (컬럼 그대로 유지, 좌우 스와이프)

`MetadataService.fetchMetadata()`가 null을 반환할 때 (5초 타임아웃 또는 파싱 실패) 사용자에게 어떻게 안내하나요?

A) 조용히 실패 — 제목/설명 입력 필드를 빈 상태로 표시, 사용자가 직접 입력

## 섹션 8: 에러 처리 및 엣지 케이스

**Q18. 슬러그 중복 시 처리**

**Q19. 북마크 일괄 Import 중 일부 실패 처리**

A) 성공한 것만 저장, 실패 항목은 무시 (결과 요약만 표시)  
B) 실패 항목 목록을 사용자에게 표시 (재시도 또는 수동 입력 유도)  
C) 하나라도 실패하면 전체 롤백

> **추천: A**  
> 크롬 북마크 HTML에는 수백~수천 개의 항목이 있을 수 있습니다. C(전체 롤백)는 단 하나의 파싱 실패로 전체 Import가 무효화되어 사용자 경험이 최악입니다. B(실패 목록 표시)는 실패 항목이 많을 경우 UI가 복잡해지고, 크롬 북마크 파싱 실패는 대부분 빈 URL이나 폴더 항목 같은 무의미한 데이터입니다. A는 성공한 것을 최대한 저장하고 "300개 중 295개 추가, 5개 스킵"처럼 결과 요약만 보여주는 것이 가장 실용적입니다. `importFromHtml()`의 반환 타입 `{ imported: number; failed: number }`도 이미 A 방식을 전제하고 설계되어 있습니다.

[Answer]: B
